# Audit and Remediation Report — 2026-11-01

## Scope

The audit covered the committed baseline `f64e65c` (the “verified typed
interpreter baseline”): source modules, CLI, tests, fixtures, Cabal/Stack
configuration, README, and `docs/plans`/`docs/process`.

The baseline was buildable and all 60 committed tests passed, but the tests
encoded several defects and the implementation was much narrower than its
documentation implied.  The remediation replaced the baseline with a complete
interpreted ProtoHaskell pipeline rather than patching each symptom in place.

Verified final state:

```text
cabal build all       OK
cabal test            OK (all active fixture/inline cases)
```

The final count is recorded by the test runner and in the README.

## Correctness findings

| ID | Finding | Severity | Remediation |
| --- | --- | --- | --- |
| C1 | Prefix `-` was desugared to `pred`, so `- 1` evaluated to `0` and `- 2 + 3` to `4`. | critical | Prefix minus now maps to `negate`; subtraction is the ordinary infix `-` primitive. Fixtures cover `- 1`, `- 2`, and subtraction. |
| C2 | Infix spans were inverted/truncated: `1 + 2` reported a span beginning at `+`, not at `1`. | high | Operator application spans are built from the left operand start to the right operand end. Parser tests assert full-expression spans and left nesting. |
| C3 | The REPL was stateless, re-parsed each line, required a final expression in every declaration line, and crashed at EOF. | high | The REPL now accumulates declarations, parses declaration-or-expression input, keeps the environment, handles EOF, and supports `:load`/`:reload`/`:browse`/`:type`/`:core`/`:source`/`:module`/`:quit`. |
| C4 | Evaluation errors had no source file or span. | high | `EvalError` carries the source file.  Spans remain `<unknown>` because Core intentionally does not retain spans; this residual is documented. |
| C5 | End-of-input parse errors reported `<unknown>` locations. | medium | The parser reports zero-width end-of-input spans (for example `1 +` reports `1:4`) and tests assert them. |
| C6 | Duplicate-name diagnostics leaked Haskell `Show` output for spans. | medium | Rename diagnostics use the normalized renderer and stable messages; fixtures assert fragments. |
| C7 | REPL values and types leaked internals (closures, `#id` suffixes, non-normalized type variables). | medium | Values are rendered through a bounded pretty-printer; schemes are normalized (`t0`, `t1`, …); user constructor names are displayed without unique ids. |
| C8 | The old parser swallowed atom failures and greedily consumed declaration values, producing misleading separator errors. | medium | The parser is a layout-aware recursive-descent parser with explicit declaration blocks, operator fixities, and contextual errors. |
| C9 | Inference dropped substitutions in lambda/let/annotation paths. | low | Inference now applies a single mutable substitution, generalizes after solving, and checks signatures by skolemization. Occurs/annotation tests cover the critical paths. |

## Residual risks

1. **Evaluation spans.** Core has no source spans, so runtime errors render
   `span=<unknown>`; they do carry the source file and a stable message.
2. **No Core type checker.** Elaboration is tested end-to-end, but a Core-level
   type checker (recommended by the book) is still future work.
3. **Class boundaries.** Default methods, method-specific constraints, and
   `deriving` are rejected explicitly rather than implemented.
4. **GADT syntax only.** GADT-style declarations are checked as ordinary ADTs;
   existential result types and GADT-specific typing are not implemented.
5. **Layout inside parentheses.** Layout insertion is suppressed inside
   brackets; explicit braces/semicolons are required there.
6. **Devenv validation.** The Nix store ran out of space while realizing the
   devenv shell, so `devenv shell` was not verified in this environment.
   `cabal build`/`cabal test` were verified with the Nix-provided GHC 9.10.3.
7. **Warning-free build.** `-Wall` still reports partial-function and unused
   binding warnings in parser/pretty-printing helpers; they are not semantic
   failures, but a future cleanup pass should eliminate them.
